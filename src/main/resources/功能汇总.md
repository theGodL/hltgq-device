# hltgq-device 功能汇总

> 用途：统一整理本项目自建设以来交付的全部功能，按功能域分章，每项功能统一按「功能描述」「解决的问题」两个维度展开，供项目验收、交接与后续迭代参考。
> 范围：截至 2026-09-30 已交付并落地的功能。

## 一、项目概述

### 1.1 项目定位

hltgq-device 是一套部署于业务内网（Docker 容器 `10.68.18.4:18686`）的**大华 ICC 视频监控代理与智能巡检服务**。它在业务平台与大华 ICC 视频平台（`60.175.44.252:9443`）之间提供统一能力层：

- 向上：为 PC 端与 H5 移动端提供视频监视、云台控制、录像回放页面与标准 REST 接口；
- 向下：封装大华 ICC 的鉴权、设备树、实时流、录像、云台、IVSS 智能事件等原始能力，屏蔽其协议细节与历史坑；
- 向内：对全域摄像机执行周期性视频质量自动巡检，故障自动生成告警并联动工单，形成「检测 → 告警 → 处置 → 恢复关警」的闭环。

一句话概括：把大华 ICC 的原始视频能力"翻译"成业务系统好用的接口与页面，并把"视频坏了没人知道"变成"自动发现、自动告警、自动派单"。

### 1.2 技术栈与运行环境

| 项 | 内容 |
|---|---|
| 语言 / 框架 | Java 1.8 + Spring Boot 2.7.6（Maven 构建） |
| 大华对接 | 大华 ICC Java SDK（java-sdk-oauth / java-sdk-common / java-sdk-core 1.0.13.12）+ 原生 HTTP 接口 |
| 数据库 | KingbaseES V8（人大金仓，PostgreSQL 协议驱动） |
| 缓存 / 会话 | Redis（集群模式，StringRedisTemplate） |

| 前端播放 | hls.js（PC / H5 统一播放器） |
| 部署形态 | Docker（Dockerfile / docker-compose.yml / deploy.sh），适配 ARM64（麒麟）环境 |
| 对外入口 | 内网直连 `http://10.68.18.4:18686`；nginx 统一前缀 `http://220.179.1.110:8081/hltgq-device/` |

### 1.3 功能域地图

12. 部署与运维支撑

## 二、大华 ICC 平台对接基础能力

### 2.1 ICC 统一鉴权（OAuth2）

**功能描述**：对接大华 ICC 的 OAuth2 password 模式鉴权接口，统一获取并管理 accessToken；封装 SDK 配置构建逻辑（host 仅传 IP 不带协议前缀），所有业务接口调用前统一由 `DahuaAuthService` 提供有效 token。

**解决的问题**：
- 视频能力分散对接时，每个调用点都要重复处理登录逻辑，维护成本高、易出错；
- 大华 SDK 配置存在隐式坑（host 带 `http://` 前缀会导致鉴权失败），统一封装后一次性规避，避免反复踩坑调试。

### 2.2 Token 预热

**功能描述**：使用后台线程（`icc-token-preWarm`）在服务运行期间主动维护 token，业务请求到来时直接取用已就绪的 token，而不是等到首个请求才发起鉴权往返。

**解决的问题**：
- 首个访问请求需等待完整鉴权链路，页面打开慢；
- 高峰期批量请求集中触发鉴权，放大 ICC 侧压力；
- token 过期瞬间的请求失败造成偶发不可用。

### 2.3 设备树查询与在线状态

**功能描述**：封装 `GET /api/dahua/device-tree`，从 ICC 拉取设备树并提供给前端（侧边栏懒加载）；返回结构包含节点在线状态（isOnline 0/1）与摄像机类型（cameraType：1=枪机 2=球机 3=半球 4=云台）；服务层用独立结果对象区分"接口调用失败"与"节点无子节点"两种情形。

**解决的问题**：
- 前端需要"组织 → 设备 → 通道"的完整层级来组织视频界面，ICC 原始返回结构对前端不友好；
- "平台异常"与"真的没有设备"若不区分，会把调用失败当空数据处理，造成误判。

### 2.4 视频通道 ID 归一化

**功能描述**：前端可能只拿得到纯设备编码（如 `1000230`），ICC 要求完整格式 `deviceCode$channelType$streamType$channelSeq`。服务端统一归一化：已含 `$` 的原样使用；短格式自动补齐为 `{code}$1$0$0`；并校验第一个 `$` 后必须是 `1`（视频通道），否则记录告警日志。

**解决的问题**：
- 前后端对通道 ID 格式认知不一致导致的调用失败；
- 非视频通道（如闸门控制通道）误传时及时发现，避免无效请求打到 ICC。

### 2.5 通道信息自动补全

**功能描述**：提供 `GET /api/dahua/channel-info?channelId=` 接口，按通道编码返回通道名称、类型、所属站点 ID 等上下文信息，供页面在只持有 channelId 时自动补全其余参数。

**解决的问题**：
- 平台侧（列表、地图）点击进入视频页时往往只能提供通道 ID，缺名称、类型等参数；自动补全后前端零拼参、无需多次查询设备树。

## 三、实时视频与 HLS 反向代理

### 3.1 实时流地址获取

**功能描述**：提供 `GET /api/dahua/stream-url`，向 ICC 申请实时流（HLS）地址后做三步处理：网关地址修正（ICC 返回的 NVR 地址在内网不同网段，需替换为本服务可达的内网地址）、附加鉴权 token、包装为经本服务代理的 `/api/dahua/hls-proxy?url=...` 地址返回前端。

**解决的问题**：
- NVR 流媒体端口（7086）仅内网可达且无鉴权保护，浏览器无法直连；
- ICC 返回的原始地址跨网段不可达，需统一出口做地址修正与鉴权透传。

### 3.2 智能码流探测（主 / 子码流优选）

**功能描述**：播放前对通道做一次性码流探测并缓存结果（`channelStreamStrategy`，值为 `main` / `sub`）：
1. 拉子码流 m3u8 → 拉首条 TS → 扫 PMT 判编码；
2. 子码流为 H.264 → 直接出子码流（带宽低、无需转码）；
3. 子码流为 HEVC → 探测主码流：主码流为 H.264 → 出主码流；主码流也不可用 → 回退子码流由代理层转码；
4. 主码流缓存失效时自动降级重探测；探测设连接 3s / 读 5s 超时，拉取失败返回"流不可用"，避免把不可用误判为 H.264 直出。

**解决的问题**：
- 无脑选主码流则带宽/转码开销大，无脑选子码流则部分设备子码流恰为 HEVC 无法直出；
- 播放中在代理层中途切换 m3u8（主/子切换）会导致 PTS 不连续、播放卡死，探测前置到播放前一次性完成，彻底规避；
- 把"流不可用"误判为 H.264 会向前端返回无效地址，直接触发播放器 `manifestLoadError`。

### 3.3 HLS 反向代理

**功能描述**：所有 HLS 请求（m3u8 清单与 TS 分片）统一经 `GET /api/dahua/hls-proxy/{filename}?url=` 转发：
- 解码 url 后将 `$` 替换回 `%24`（NVR 要求路径中 `$` 必须编码，否则返回错误内容）；
- 附加鉴权：`token` 参数 + `X-Subject-Token` 请求头；
- m3u8 清单改写：清单中的 TS 分片地址统一改写为经本代理的相对路径 URL，保证每个分片都带鉴权；
- TS 文件名保留，供 hls.js 识别媒体类型；底层 HTTP 连接 keep-alive 复用。

**解决的问题**：
- 浏览器直连 NVR 不可达且无鉴权，代理统一出口后，前端只认一个稳定地址；
- 若 m3u8 中的分片地址不经过代理改写，分片请求会绕过鉴权/网络出口导致 401/404，视频无法播放；
- `$` 编码错误导致 NVR 返回错误内容（经典坑），统一在代理层修正。

### 3.4 HEVC（H.265）自动转码

**功能描述**：代理转发 TS 分片时扫描 PAT→PMT，`streamType==0x24` 判定为 HEVC；命中后调用 ffmpeg 将该分片实时转码为 H.264 再返回浏览器；转码时按分片序号设置 **PTS 偏移 = 分片序号 × 2s**（每片独立 ffmpeg 进程，必须重新对齐时间轴）；HEVC 判定结果按流路径缓存（`hevcStreamCache`），避免每个分片重复扫描包。

**解决的问题**：
- hls.js 原生不支持 HEVC-in-TS，H.265 摄像机在浏览器端完全无法播放（裸流播放方案的最大痛点）；
- 每片独立 ffmpeg 转码若不设 PTS 偏移，播放时间轴从 0 反复重新计时，造成 `bufferStalledError` 卡顿；
- 不缓存判定结果会带来每片重复扫包的性能损耗。

### 3.5 HEVC 描述符注入（修复 fragParsingError）

**功能描述**：部分设备的 TS 流 PMT 中缺少 HEVC 描述符（tag 0x05，内含 HVCC 解码器配置），导致 hls.js 的 transmuxer 无法识别视频轨（`fragParsingError`）。代理层在转发前检测：从流中提取 VPS/SPS/PPS 构建 HVCC 描述符，改写 PMT TS 包（减少适配域填充 → 扩展 section → 插入 HEVC 描述符 → 重算 CRC32）；PMT 中已有描述符或无 HEVC 流时自动跳过。

**解决的问题**：
- 解决"能取到流、能转码但播放器仍解析失败"的深层兼容问题，是 HEVC 播放链路的最后一块拼图；
- 该问题现象在浏览器侧只报 `fragParsingError`，定位困难，服务端一次性修复后对所有设备生效。

### 3.6 nginx 统一前缀自适应

**功能描述**：nginx 代理由"每个页面/接口一个 location"改为统一前缀 location（`/hltgq-device/`，rewrite 掉前缀后转发 18686）。前端 6 个页面统一内置前缀自动感知逻辑（`APP_BASE`）：经前缀访问时自动补前缀、直连时自动不补；后端将 m3u8 中的 TS 分片地址由绝对路径改为相对路径，使两种部署入口天然兼容；后端接口路径仍写无前缀的 `/api/dahua/xxx`。

**解决的问题**：
- 前缀模式下页面跳转、接口请求、播放地址若写死绝对路径，会绕过 nginx location 直接 404；
- 统一前缀后新增页面/接口无需再改 nginx 配置，部署与扩展成本大幅降低；
- 两套入口（nginx 前缀 / 内网直连）互不影响，同一份代码通吃。

## 四、历史录像回放

### 4.1 月历录像状态

**功能描述**：提供 `GET /api/dahua/record/month-status`，对接 ICC `GetChannelMonthRecordStatus` 接口，按天返回某月是否存在录像的 0/1 序列，供前端月历打点标记。

**解决的问题**：用户需要"哪天有录像"一目了然的月历视图，而不是逐天试探；直接对接 ICC 接口对前端过于复杂。

### 4.2 录像分段查询

**功能描述**：提供 `GET /api/dahua/record/query`，对接 ICC `QueryRecords` 接口，返回指定时间段内的录像段列表（每段为一段录像文件，含起止时间）。

**解决的问题**：**回放不能跨录像文件**——前端必须先拿到分段列表，再在单个段的时间范围内申请回放流，否则请求会失败或得到错误画面；分段查询把这一硬约束前置到交互流程中。

### 4.3 回放流代理

**功能描述**：提供 `GET /api/dahua/record/stream`，按段（beginTime/endTime/recordType/recordSource）向 ICC 申请 HLS 回放流；回放流与实时流同走 7086 端口，复用同一套处理后端（token 拼接 → 内网地址修正 → 包装为代理地址）；`recordType` 必须与查询到的段类型一致。

**解决的问题**：
- 回放链路的地址修正、鉴权、编码兼容（HEVC 转码等）与实时流完全同构，复用后无需两套维护；
- recordType 不一致是 ICC 回放的常见失败原因，服务端统一从查询结果回填，前端不感知。

## 五、PTZ 云台控制

> 权限前提：仅系统管理员可用（见 5.5）。前端提交前已按 `cameraType=2`（球机）校验，后端只做通道格式校验。

### 5.1 八方向转动控制

**功能描述**：提供 `POST /api/dahua/ptz/direct`（方向：up/down/left/right/upleft/upright/downleft/downright + 速度）与 `POST /api/dahua/ptz/stop`，对接 ICC `OperateDirect` 接口；前端按住转动、松开即停。

**解决的问题**：把 ICC 原始的 direct 方向码、step 速度、command 启停模型封装为业务语义（方向 + 速度），前端无需理解平台协议。

### 5.2 镜头控制（变焦 / 聚焦 / 光圈）

**功能描述**：提供 `POST /api/dahua/ptz/lens`（zoomIn/zoomOut/focusIn/focusOut/irisIn/irisOut/stop），对接 ICC `OperateCamera` 接口，按 operateType（1=变倍 2=聚焦 3=光圈）+ direct（1=增 2=减）+ command 启停控制。

**解决的问题**：补齐球机镜头能力，水面/闸站现场可远程调整视野与清晰度，减少现场跑腿。

### 5.3 指令串行队列（防失控核心）

**功能描述**：所有云台指令进入 `PtzCommandDispatcher` 的**按通道 FIFO 串行队列**：同一通道的指令严格按序执行、不同通道互不阻塞；队列带过期丢弃规则（堆积的旧指令到达执行点时若已过期则丢弃，不再下发给设备）；接口为异步受理（立即返回受理结果，执行在后台完成）。

**解决的问题**：
- 用户快速连点/网络抖动并发下发 START/STOP，乱序到达设备会造成云台"转不停"的失控现象；
- 指令堆积（如按住方向键盘多秒产生大量指令）时把过期指令补发给设备，同样导致滞后失控；串行 + 过期丢弃从机制上根治。

### 5.4 STOP 参数复用与最小间隔

**功能描述**：按通道缓存最后一次 START 的 direct/step 参数，STOP 时复用（官方要求 STOP 必须与 START 的 stepX/stepY/direct 一致，否则设备无法停止）；START 与 STOP 之间设 150ms 最小间隔（不足时自适应补足延迟，避免异步指令乱序执行）；无历史 START 参数时跳过 API 调用；`lastStopTs` 做乱序防护，重复/过期的 STOP 不再下发。

**解决的问题**：
- 历史教训：START/STOP 值写反（0/1 互换）、STOP 用 stepX=0 与 START 不匹配，都会导致设备彻底不可控；
- 指令间隔不足造成平台侧执行乱序，是"松开按钮云台还在转"的直接原因。

### 5.5 管理员权限隔离

**功能描述**：PTZ 三个接口均标注 `@RequireAdmin`，仅系统管理员（hltgq_default_admin / administra 角色或 superAdmin）可调用，普通用户请求返回 403；前端云台面板显隐由 `GET /api/dahua/auth/current-user` 的 `isAdmin` 决定，固定枪机通道的面板置灰/隐藏并提示"当前设备不支持云台控制"。

**解决的问题**：
- 云台误操作（转动镜头偏离监测目标）会直接影响业务，必须权限收敛；
- 前端显隐 + 后端拦截双重保障，普通用户即使构造请求也无法操作。

## 六、IVSS 智能事件接入

> 边界说明：智能分析（AI 识别类告警）由大华 IVSS 平台实现，本服务只做**事件接入与转发**，不自研智能分析；本服务自研的是图像质量类巡检（见第七章）。

### 6.1 事件订阅与自愈刷新

**功能描述**：向 ICC `subscribe/mqinfo` 接口订阅报警事件：回调地址指向本服务 `POST /api/dahua/event/receive`；订阅标识 magic = 回调地址的 `IP_端口`；订阅类型为"只要报警"（eventType=2）、订阅全部报警类型（subscribeAll=1，alarmType 码值随现场平台动态生成、无静态码表，处理侧按 `alarmTypeName` 透传）；正确处理 orgs/nodeCodes 并集规则（仅按 orgs 过滤时必须显式传 `nodeCodes=[]`，否则过滤失效）。应用启动即异步订阅，并**每小时整点幂等刷新一次**。

**解决的问题**：
- ICC 平台侧订阅可能因平台重启/人工误删而丢失，本侧无感知会导致事件链路静默中断；整点幂等刷新实现自愈，无需人工介入；
- 订阅参数并集语义是官方文档的隐蔽坑，处理不当会造成订阅范围失控或过滤失效。

### 6.2 回调接收（立即响应 + 异步处理）

**功能描述**：`POST /api/dahua/event/receive` 收到事件后立即返回成功（`{"code":"0","message":"成功"}`），实际业务处理放入专用线程池异步执行；该回调接口位于登录拦截白名单（ICC 无法携带业务会话）。

**解决的问题**：ICC 对回调响应有超时要求，若在回调线程内同步落库、解析站点等业务逻辑，一旦超时会被判定投递失败并重发，造成重复与丢失并存。

### 6.3 事件处理与幂等去重

**功能描述**：仅处理 `category=alarm && method=alarm.msg` 的报警消息；按事件 uuid 做去重（1 小时窗口）；由 nodeCode 解析到设备表与所属站点（限定视频类型 #5#，防误挂）；alarmGrade 映射告警级别；按 alarmStat 区分"发生（1）/ 消失（2）"；按 alarmTypeName 透传生成告警内容。

**解决的问题**：
- 网络抖动场景下同一事件重复投递，无幂等会产生重复告警；
- 事件必须挂接到正确的站点与设备上下文才能被业务使用，nodeCode→设备→站点的解析链路解决归属问题。

### 6.4 轮询兜底补偿

**功能描述**：在巡检轮次内，按 `lastPullTime` 游标分页拉取 ICC 最近事件（`alarm-record/page` 接口），补偿订阅回调可能丢失的事件；拉取到的事件与回调共用同一处理链路（幂等去重天然防重复）。

**解决的问题**：订阅回调依赖 ICC 主动推送，网络抖动或平台侧异常时事件可能丢失；轮询兜底作为第二通道，保证"发生过的报警最终一定会进入业务系统"。

## 七、视频故障自动巡检

> 本服务自研的核心能力：不依赖人工看屏，周期性对全域摄像机做"在线性 + 取流性 + 图像质量"三层检测，自动发现视频故障。

### 7.1 轮巡调度框架

**功能描述**：默认每 30 分钟一轮（cron `0 5,35 * * * ?`，错峰避开整点站点同步任务 5 分钟）。一轮的完整流程：
1. **轮级登录检查**：token 获取失败自动重试（默认 3 次），仍失败则整轮中止（宁可跳过，不带病检测）；
2. **通道池构建**：复用站点同步的设备树遍历结果；设备树遍历不完整时整轮中止（**数据缺失不检测，防止误报/误关**）；
3. **线程池并发检测**：默认 4 路并发；总预算 = 批数 × 单路硬超时，预算耗尽的通道被取消且**不参与防抖判定**（计数保持，"没检测到"绝不等于"已恢复"）；
4. **巡检留痕落库**（见 9.1）；
5. **防抖判定 → 告警新增/恢复**（见 7.4）；
6. **IVSS 事件轮询兜底**（见 6.4）。

轮次用 CAS 防重入（上一轮未结束则本轮跳过），并提供状态快照（RoundSnapshot）与手动触发能力（见 12.2）。

**解决的问题**：
- 视频故障从"靠人发现"变为"系统主动发现"，覆盖无人值守时段；
- 大批量通道检测的耗时不可控问题：总预算 + 单路超时 + 并发数三重约束，保证每轮检测在可预期时间内完成；
- 并发/超时/异常场景下的误判防护：所有"没有结论"的通道一律不动既有告警状态。

### 7.2 故障识别体系（15 类）

**功能描述**：内置 15 类故障枚举（`VideoFaultType`），分三层：

| 层 | 故障 | 判定链路 |
|---|---|---|
| A 层·流协议（3 类） | 信号丢失 SIGNAL_LOSS / 取流异常 STREAM_ERROR / 登录失败 LOGIN_FAIL | 设备离线 → 信号丢失；在线但地址获取失败、流探测失败或抽帧为空 → 取流异常 |
| B 层·图像质量（7 类） | 过亮 TOO_BRIGHT / 过暗 TOO_DARK / 偏色 COLOR_CAST / 黑白 GRAYSCALE / 模糊 BLUR / 低对比度 LOW_CONTRAST / 噪声 NOISE | ffmpeg 抽帧 → 图像质量分析（见 7.3） |
| C 层·进阶（5 类，二期预留） | 抖动 JITTER / 条纹 STRIPE / 畸变 DISTORTION / 场景变更 SCENE_CHANGE / 云台失控 PTZ_OUT_OF_CONTROL | 枚举已定义（含 level 与二期标记），一期不启用 |

**解决的问题**：
- 视频故障类型杂、现象多，统一成标准枚举后，告警内容、统计口径、后续扩展（二期）全部有据可依；
- 登录失败与取流异常分开描述，运维定位方向不同（整轮登录失败=平台侧问题，单路取流异常=设备侧问题）。

### 7.3 图像质量分析（纯 Java 像素统计）

**功能描述**：检测前用 ffmpeg 抽帧（连接超时 8s、宽度降采样到 320、JPEG 质量 2、硬超时强杀、临时文件用后即删）；图像分析为**纯 Java 像素统计**（不依赖 OpenCV）：亮度均值、暗/亮像素占比、饱和度、Laplacian 方差（清晰度）、噪声残差等指标，全部阈值配置化（`video-alert.threshold.*`）。

**解决的问题**：
- 引入 OpenCV 等重依赖会大幅增加 ARM64 / 麒麟环境的部署成本与故障面，纯 Java 实现零额外依赖；
- 抽帧内容（临时文件）即用即删，不占用磁盘、不残留数据。

### 7.4 防抖状态机（AlertDebouncer）

**功能描述**：按"通道 × 故障类型"维护有符号连续计数（正数=连续异常轮数，负数=连续正常轮数）；连续 N 轮异常才产生告警（detectThreshold）、连续 M 轮正常才恢复（recoverThreshold）；`activeFaults` 跟踪当前在告警中的故障；豁免故障（见 7.5）跳过判定且计数不变。

**解决的问题**：
- 单轮偶发误检（网络抖动、瞬时噪点、光线突变）直接告警会造成误报风暴；
- 恢复侧抖动（时好时坏）会造成告警反复开关，运维被骚扰；连续轮次确认机制让告警"该报才报、该关才关"。

### 7.5 夜间豁免

**功能描述**：默认 18:30 - 07:30 时段内，对"黑白 GRAYSCALE / 过暗 TOO_DARK / 偏色 COLOR_CAST"三类故障**跳过防抖判定**（不新增告警、也不恢复告警），巡检留痕照常按原始检测结果落库（统计口径不受影响）。

**解决的问题**：摄像机夜间切红外后画面天然呈黑白、无补光点位天然偏暗、夜视偏色属物理正常现象——不豁免会导致夜间大面积误报，而豁免只影响告警不影响统计，检测数据仍完整。

### 7.6 恢复抑制窗口

**功能描述**：告警恢复（关闭）后，对同一通道同一故障在抑制窗口（默认 360 分钟）内的再次检出做挂起处理（suppressedPending），窗口结束前不重复告警；窗口过后若仍异常则补发。

**解决的问题**：接触不良等间歇性故障会导致"坏了-好了-又坏了"的告警反复开关；抑制窗口给现场留出处置缓冲，避免骚扰。

### 7.7 检测异常保护（防误关）

**功能描述**：三处独立防护：
1. 单路检测异常/超时被取消的通道，不进入"本轮已检测集合"，防抖计数保持原值（不视为正常）；
2. 轮级登录失败、设备树不完整时整轮中止，不做任何告警新增/恢复；
3. 恢复统计仅计入"实际关闭条数 > 0"的恢复（人工已关闭的行不重复计数）。

**解决的问题**：把"系统检测不到"误判为"设备已恢复"，会错误关闭真实告警并联动关闭工单——这是巡检类系统最危险的误操作，三处防护确保"没有结论时什么都不做"。

## 八、告警与工单闭环

### 8.1 告警自动入库

**功能描述**：巡检发现的故障（含恢复）自动写入告警表 `t_auto_hltgq_water_alert`：告警编号 `GJ + yyyyMMddHHmmss + 3 位序号`；内容格式 `{站点名}-视频 {故障名}！`；状态 `#1#`（待处理）/ `#4#`（已关闭）；类型 `#2#`（异常）/ `#3#`（智能）；以 site + device + content 三字段做去重；字段列做动态适配（兼容库表列差异）。IVSS 智能事件的告警同样入该表（按 alarmTypeName 生成内容，类型走智能）。

**解决的问题**：
- 与 mq 平台（主业务平台）的告警同表、同编号规则、同状态语义，业务侧无需区分告警来源，统计大屏天然兼容；
- 无去重会产生重复告警记录，三字段去重确保同一站点同一故障只有一条活跃告警。

### 8.2 告警恢复自动关警

**功能描述**：故障连续正常达到恢复阈值后，自动将该站点该故障的**待处理（#1#）**告警置为已关闭（#4#）；返回实际关闭条数（0 条表示无需关闭，如人工已处理）。

**解决的问题**：故障恢复后告警长期挂着的"僵尸告警"问题；只关 #1# 状态的不越权覆盖人工处置记录。

### 8.3 工单自动联动

**功能描述**：告警产生时自动创建工单（表 `t_auto_hltgq_water_work_order`）：工单编号 `GD + 时间 + 序号`；`createIfAbsent` 幂等创建；按站点归属解析责任组织（库上 `00000003` / 库下 `00000004` 防汛办）；工单类型 `#hxqm#`（设备故障抢修）/ `#pfqj#`（安全隐患整改）；告警恢复时按内容匹配联动关闭工单（仅关闭 `#1#` 待处理状态）。

**解决的问题**：
- "告警有人报、处置没人管"的断链问题：视频故障自动派单到责任单位/人；
- 恢复后工单自动回关，形成"检测 → 告警 → 工单 → 处置 → 恢复关单"完整闭环。

### 8.4 活跃告警查询接口

**功能描述**：提供 `GET /api/dahua/alert/active`：支持按通道聚合汇总（每个通道的活跃告警数）与查询指定通道的活跃告警明细（告警表 JOIN 设备表取站点上下文）。

**解决的问题**：H5 列表页的告警角标、实时监控页的"AI 检测状态栏"需要真实告警数据（有告警 → 红底显示检测到的事件名；无 → 绿底正常），该接口一次满足两类消费场景。

## 九、站点与设备数据同步

### 9.1 视频设备表同步

**功能描述**：把 ICC 视频通道落成业务设备表中的正式设备：以设备 `code = 通道 devicecode`（含 `#5#` 视频类型限定，防与闸门等其他类型误命中）为权威匹配键；设备名按"站点名 + 摄像机#"规则派生；提供 `lookupOrCreateDevice`（查找或创建）、`findDeviceByCodeOrName`（按编码/名称回填补全 code）；字段列动态适配。

**解决的问题**：
- 视频通道在业务侧需要"设备"身份才能挂站、发告警、派工单；自动同步避免人工录入；
- 匹配键不唯一会导致错误挂接（如闸门通道与视频通道编码相似），#5# 类型限定从键上根治。

### 9.2 站点同步与通道挂靠（四态处理）

**功能描述**：`StationStatusSyncService` 每小时整点同步（启动时另做一次异步同步，不阻塞启动）：
- 递归遍历 ICC 设备树，收集全部视频通道（构建通道池，供巡检与 channel-info 复用）；
- **四态处理**：新通道（新增设备并挂靠站点）、兜底站（父节点在业务库无对应站点时挂入兜底站，不丢数据）、迁移行（站点-设备改造后的遗留数据行处理）、业务站（站点已存在时直接挂靠）；
- 父节点名称别名纠偏（PARENT_NAME_ALIASES，如"荞麦岭泄洪闸"归一到"荞麦岭泄洪河"）；特定组织过滤（FILTERED_ORG_NAMES）；
- ICC 中消失的通道标记离线（遍历失败时跳过该步，防误标）；
- 站点侧仅写监测类型 epjutj 的 `#5#`（视频）标记与系统字段（D1 决策，不越权改业务字段）。

**解决的问题**：
- ICC 设备树与业务站点库持续漂移（新增/改名/移除摄像机），纯人工维护必然滞后；
- 名称口径不一致（同一位置多种叫法）导致挂靠失败；兜底站策略保证"宁可挂兜底、不可丢设备"。

### 9.3 站点-设备数据架构改造与存量迁移

**功能描述**：对存量数据模型做了一次架构级改造：
- **背景**：旧形态为每路视频建一个"xxx-视频"影子站点（视频与站点混为一谈）；
- **目标形态**：视频作为站点的**监测类型**（站点表 epjutj 字段追加 `#5#` 标记），站点-设备改为 1:N 关系（一个站点挂多台摄像机）；
- **交付物**：三方评审说明文档、迁移五步脚本（m1 预检 / m2 迁移 / m3 对账 / m4 回退 / m5 清理）、dry-run 全量映射核对清单（175 站点行 / 175 设备 / 95 告警 / 103 工单，含灰度 6 台）；
- **执行**：按窗口序列执行（停旧服务 → 快照 → m1 → m2 灰度 → m3 对账 → m2 全量 → 启动新代码）；2026-09-24 退役行物理删除并生成全字段备份存档（供人工恢复）。

**解决的问题**：
- 影子站点导致站点数量虚增、统计失真、站点-设备关系混乱（一个"站点"实际只是一路视频）；
- 数据迁移必须可控可回退：五步脚本 + dry-run 核对 + 灰度 + 快照备份，把迁移风险降到可接受；
- 新架构下站点统计、监测类型、告警归属全部语义正确。

## 十、巡检留痕与采集统计

### 10.1 巡检留痕落库

**功能描述**：每轮巡检的**每通道原始结果**写入留痕表 `t_auto_hltgq_water_video_patrol`（不过防抖、按原始检测落库），结果三态：ok（正常）/ fail（检出故障）/ error（检测异常或超时）；以 `UNIQUE(round_time, channel_code)` + `ON CONFLICT DO NOTHING` 保证幂等；留痕落库异常只记日志，不影响主流程。

**解决的问题**：
- 巡检"检了什么、结果如何"需要完整过程证据，供统计与追责；
- 统计口径与告警口径分离（统计看原始检测，告警看防抖确认），两者互不干扰；
- 轮次重跑（手动触发与定时撞车）不会写重复行。

### 10.2 采集统计接口

**功能描述**：提供 `GET /api/dahua/video/patrol-stats`（当日 / 指定区间）：应检数 = 通道数 × 已结束的完整轮次（进行中的轮次不计入，防分母虚高）；实检数 / 正常 / 异常 / 检测失败分别统计；查询范围上限 730 天；输出结构与 mq 平台 collect-stats 同构，供统计大屏"视频数据"行直接展示。

**解决的问题**：
- 上级考核的"视频巡检采集率"有了自动化、可审计的数据来源；
- 手工统计既慢又不可靠，接口化后大屏/报表直接取数。

## 十一、登录鉴权与权限体系

### 11.1 全量登录校验（拦截器）

**功能描述**：`AuthInterceptor` 对所有请求做登录校验：从 `X-Session-Id` / `Authorization` / Cookie 中提取会话，经 Redis（HGETALL 会话 Hash）解析用户上下文；固定白名单仅放行 `/error` 与 `/api/dahua/event/`（ICC 回调）；未登录请求 PC 端 401/302 跳平台登录页。

**解决的问题**：
- 视频接口与页面默认全量受保护，杜绝"视频裸奔"（未登录即可看实时画面）；
- 会话与业务平台统一（Redis 共享），平台登录一次，视频页免登录。

### 11.2 管理员权限（@RequireAdmin）

**功能描述**：敏感操作（PTZ 云台）标注 `@RequireAdmin`；`RolePermissionService` 判定链：超管（superAdmin）直接通过 → 角色码匹配（hltgq_default_admin / administra）→ 本地缓存 5 分钟 → Redis 角色缓存 → 查库兜底；`GET /api/dahua/auth/current-user` 向前端输出 isAdmin 供界面显隐。

**解决的问题**：
- 权限判定若每次查库/查 Redis 会拖慢高频接口（云台长按会产生大量请求），多级缓存平衡性能与一致性；
- 前端显隐与后端强校验双保险。

### 11.3 PC / H5 登录页区分跳转

**功能描述**：拦截器按请求路径（`/mobile/`）或 Referer 判定 H5 请求，未登录时分别 302 跳转 PC 登录页或 H5 登录页（`http://220.179.1.110:8081/hlt/#/login/user/login`）。

**解决的问题**：手机用户被跳到 PC 登录页体验极差（布局不适配），自动区分后移动端闭环体验完整。

### 11.4 异常语义与降级策略

**功能描述**：响应语义严格区分：401=未登录（跳登录）、403=无权限（拒绝）、503=会话服务（Redis）不可用；**503 场景不做降级放行**。

**解决的问题**：缓存/会话服务故障时若"放行保可用"，等于鉴权形同虚设；宁可短暂不可用，不可越权，安全优先。

## 十二、PC 与 H5 页面体系

### 12.1 PC 端页面

**功能描述**：三个页面：
- `monitor.html`：设备树侧栏（懒加载）+ 视频网格（1/4/6/9/12/16 布局切换）+ 抽屉式 PTZ 面板 + 搜索 + 全屏；
- `playback.html`：回放（月历打点 + 录像分段列表）；
- `viewer.html`：单通道视频预览 + 云台控制（从监控页进入的单路详情页）。

**解决的问题**：值班室桌面端的集中监视、多路同屏、快速定位与云台操作需求。

### 12.2 H5 移动端五页面

**功能描述**：
- `monitor.html`：视频监视列表（站点/设备列表 + 告警角标统计）；
- `live.html`：单路实时监控 + 云台条；
- `playback.html`：回放列表（月历 + 分段）；
- `playback-player.html`：回放播放（倍速 / 暂停）；
- `live-popup.html`：轻量单路实时监控页（仅需传 channelId，名称/类型/站点上下文自动补全；导航栏自带返回按钮，有历史返回上页、直开兜底回列表页）。

**解决的问题**：
- 移动端随时随地看视频（现场巡查、外出值守场景）；
- `live-popup` 解决平台（列表/地图）点击后单路查看的集成诉求：前端零 API 对接、只拼一个 channelId。

### 12.3 移动端体验加固

**功能描述**：
- iOS 兼容：muted + playsinline 自动起播（防强制全屏）、被拦截时静默显示播放按钮、点击视频区亦可起播；
- 防失控加固：云台按住转动、松开/快速点按/切后台一律自动停止；
- 交互适配：触摸 + 鼠标双事件绑定、安全区吸收（刘海屏）、全屏自适应无滚动条；
- 跳转闭环：页面间返回有历史走 history.back()、无历史兜底回列表页，不跳出业务闭环。

**解决的问题**：移动端浏览器（尤其 iOS Safari）的播放限制与触摸交互差异，若不做适配会出现"点了不放、放了不停、返回跳出"等体验问题。

### 12.4 平台集成方式

**功能描述**：视频 H5 自成闭环，平台侧只需一个入口地址（零 API 对接、零额外配置），支持三种集成：菜单/按钮整页跳转（推荐）、iframe 嵌入（需加 `allow="autoplay; fullscreen; encrypted-media; picture-in-picture"` 属性）、live-popup 页面跳转单路监控。

**解决的问题**：平台前端接入视频能力的成本从"对接一堆接口"降为"配一个入口地址"；文档（大华视频H5方案.md）给出集成注意事项（未登录 302 在 iframe 内的处理、容器高度等）。

## 十三、部署与运维支撑

### 13.1 Docker 部署

**功能描述**：提供 Dockerfile、docker-compose.yml、deploy.sh 全套部署脚本；针对 ARM64（麒麟）国产化环境做了适配（ffmpeg 与运行依赖）。

**解决的问题**：信创环境（国产 CPU + 国产 OS）下的部署一致性；一键部署降低现场交付成本。

### 13.2 运维接口与状态快照

**功能描述**：视频告警模块提供运维接口：手动触发一轮检测（异步受理，上一轮未结束则拒绝）、当前轮巡状态快照（RoundSnapshot：轮次状态/通道总数/在线数/完成数/新增告警数/恢复数/各通道结果摘要/轮次备注）。

**解决的问题**：应急处置（不等 30 分钟定时）与线上排查（本轮跑没跑、跑到哪、哪路异常）不依赖翻日志。

### 13.3 定时任务总览

| 任务 | 频率 | 说明 |
|---|---|---|
| 视频故障巡检轮巡 | 每 30 分钟（5、35 分） | 错峰避开整点任务 |
| 站点状态同步 | 每小时整点 | 另在启动时异步执行一次 |
| IVSS 事件订阅刷新 | 每小时整点 | 幂等刷新，防订阅丢失自愈 |
| IVSS 事件轮询兜底 | 随巡检轮次 | 补偿回调丢失 |

**解决的问题**：后台自动行为集中可视，运维交班有据可查。

## 十五、总结

本项目围绕"让视频监控真正可用、好管"这一目标，分四层交付能力：

1. **看得见（播放链路）**：从 ICC 取流到浏览器播放全链路打通，重点攻克了 HEVC 兼容（转码 + PTS 对齐 + 描述符注入）、码流优选、鉴权代理、nginx 前缀适配四大难题，PC 与 H5 双端可用；
2. **控得住（操作链路）**：云台/镜头控制从协议封装到防失控机制（串行队列 + 参数复用 + 最小间隔）完整闭环，权限严格收敛到管理员；
3. **管得好（数据链路）**：设备/站点自动同步、站点-设备 1:N 架构改造与存量迁移，视频资产与业务数据模型正确对齐；
4. **护得牢（运维链路）**：15 类故障自动巡检 + 防抖/夜间豁免/抑制窗口三重降噪 + 告警工单闭环 + 留痕统计，视频运维从人肉巡检升级为系统自动闭环。

配套文档：《大华视频对接方案.md》（协议级对接细节）、《大华视频H5方案.md》（移动端与平台集成）、《站点-设备数据架构改造评审说明.md》（架构改造决策与评审）、《功能汇总.md》（本文档）。
