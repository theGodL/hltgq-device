## 一、背景与现状

### 1.1 现状（代码与数据事实）

- 大华 ICC 设备树视频通道（截至 2026-09-23 存量核实：巡检累计覆盖 175 个、当前每轮 172 个，见 11.1 / 11.3-B），在**站点表**中各占一行独立视频站点（`epjutj='#5#'`），与已有站点重名时追加"-视频"后缀（如"夏家湖渡槽-视频"；再撞名时数字递增"-视频2"等），由 hltgq-device 每小时整点同步维护（`StationStatusSyncService`）；
- 存量规模口径（site 实测，见 7.3-c；2026-09-23 晚 site 只读复核更正，见 7.6）：站点表视频行 **175 条 / 视频设备 175 台**，1:1 完整、无孤儿设备；与通道数一致（巡检累计 175 = 视频行 175；当前活跃 172 + 僵尸行 3 台，见 11.3-B；通道消失遗留的行同步只标离线、不删除）；设备表实测共 357 行，其中 **type 为空值 9 台**并入存量分类清单核对（见 9.1-A1）；
- **设备表**中每个视频站点对应 1 台视频设备（`type='#5#'`），站点-设备严格 **1:1**（`DeviceTableService`）；
- hltgq-device 已具备"通道 → 业务站点"的匹配能力：候选链「NVR 名 → 去"上游/下游"后缀 → 人工别名 → 组织名兜底」逐级尝试——每级先要求非视频行唯一命中，否则跟随同名视频行已挂上级（`resolveParentId`），最终唯一命中才采用；把视频站点用 `ahieto`"挂上级"（2026-09-22 已有业务人工裁决的别名先例，如"荞麦岭泄洪闸"→"荞麦岭泄洪河"、"二号渡槽"→"2#渡槽"）。**但视频站点行本身仍是独立行**，未并入业务站点。

### 1.2 问题（为什么不合理）

| # | 现象 | 影响 | 根因 |
|---|---|---|---|
| 1 | 每个视频通道一个站点行 | 站点表被视频行稀释，站点规模虚增 | 视频本质是"设备"，却被当"站点"建 |
| 2 | "xxx-视频"站点遍地 | 站点视图出现大量影子站点，业务视角混乱 | 通道名与业务站点同名时的妥协产物 |
| 3 | 站点-设备 1:1 | 表达不了"一个业务站点配多台视频" | 站点粒度错误导致关系失真 |
| 4 | 共享表混写 | 同 devicecode 混着闸门/水质/视频多行（此前已做一轮类型隔离修复） | 各服务为满足自身需要在共享表自建行 |

### 1.3 目标形态

- **视频作为业务站点的监测类型**：站点 `epjutj` 多选追加 `#5#`（如 `#1#|#4#` → `#1#|#4#|#5#`）；
- **一个业务站点对应多台视频设备（1:N）**：设备表 `site` 指向业务站点 ID；`code` 仍为通道 devicecode（唯一键不变）；
- **由 hltgq-device 定时同步维护**：通道匹配业务站点、维护站点 `#5#` 类型、维护设备关联与设备状态。

单条通道视角的形态对比：

| 表 | 现状（Before） | 目标（After） |
|---|---|---|
| 站点表 | "夏家湖渡槽"（`#1#\|#4#`）+ "夏家湖渡槽-视频"（`#5#`，devicecode=通道 code）两行 | 仅 "夏家湖渡槽" 一行（`#1#\|#4#\|#5#`） |
| 设备表 | "夏家湖渡槽-视频摄像机#"（site=视频站点 ID） | "夏家湖渡槽摄像机#"（site=夏家湖渡槽站点 ID）；同站点可挂多台通道设备 |

关系链（改造后）：

```
ICC 通道（devicecode = 1000231$1$0$10）
    │ 匹配（NVR名/别名/组织名 → 业务站点，唯一命中才挂）
    ▼
站点表·业务站点行（epjutj 含 #5#，如 #1#|#4#|#5#）
    ▲ site 字段指向
设备表·视频设备（code = 通道 devicecode，status = 通道在线状态）  ← 1 个站点 : N 台设备
```

## 三、具体评审要求（逐条给出结论）

### 3.1 hltgq-site：站点模型与写入权（主评审）

**S1. 站点监测类型（epjutj）承载视频**
- 是否认可：业务站点（管理所 `#2#`、闸站 `#3#`/`#1#|#4#`、片区 `#7#` 等）的 `epjutj` 追加 `#5#`，且由 hltgq-device 程序化维护；
- hltgq-device 写入边界（建议，请确认或修正）：**仅允许追加/维护 `#5#`** 与系统字段 `updated_at/updated_by`；不修改 `zzkaec`（名称）、`mivbcz`（位置）、`zebpsu`（状态）、`ahieto`（上级）等其他字段。

**S2. 站点状态（zebpsu）语义划分**
- 现状：视频站点行的 `zebpsu` 由视频通道在线状态驱动；
- 建议：改造后视频通道在线状态由**设备表 `status`** 表达，hltgq-device **不再写站点 `zebpsu`**（避免视频状态覆盖业务站点自身状态语义）；
- 若业务上要求"站点含视频且视频离线"体现在站点状态上，请另行约定规则。

**S3. 站点-设备 1:N 模型**
- 站点详情/关联设备是否支持同站点多台设备（按类型/名称区分）；
- site 侧页面逻辑是否存在"一站一设备"假设，需要哪些适配（数据模型层面确认即可，展示形式由产品/前端定）。

**S4. 匹配失败兜底**
- 通道匹配不到业务站点时（新建通道、临时设备、树外通道）：
  - 方案 A（推荐）：保留独立视频站点兜底，后续轮次匹配到再合并——不阻塞接入、成本低；
  - 方案 B：不建站，输出"待人工挂靠清单"，由人工在平台挂靠。
- 请拍板方案 A/B 或提出修正。

### 3.2 hltgq-mq：数据兼容性（会签）

**M1. "一站一设备"假设排查**
- mq 侧站点/设备逻辑（设备创建、站点遍历、统计、展示等）是否存在"一个站点最多一台同类设备"假设；
- 站点挂 N 台视频设备（1:N）后是否兼容？请输出排查结论。

**M2. 站点监测类型消费**
- 站点 `epjutj` 含 `#5#` 后，mq 按监测类型做的遍历/统计/展示（如按类型统计站点数）是否受影响？请输出排查结论。

**M3. 告警/工单关联语义**
- 既有约定不变：告警/工单 `site`=站点 ID、`device`=设备 ID、`site+device+content` 三字段去重；
- 变化点：`site` 从"视频站点 ID"变为"**业务站点 ID**"（`device` 不变）；
- 历史数据：`site` 指向旧视频站点的告警/工单，是否随迁移更新为业务站点 ID（建议更新，与 mq 侧口径对齐）——请会签。

### 3.3 业务方：挂靠规则确认

**B1. 通道 → 业务站点映射规则**
- 确认匹配链：NVR 名精确 → 去"上游/下游"后缀 → 人工别名 → 同名站点跟随 → 组织名兜底，**唯一命中才挂**（歧义不挂、留待人工）；
- 人工别名维护流程：沿用 2026-09-22 先例，特例由业务裁决后登记（如"荞麦岭泄洪闸"→"荞麦岭泄洪河"、"二号渡槽"→"2#渡槽"）。

**B2. 未匹配清单裁决**
- hltgq-device 输出"匹配失败通道清单"（日志）；业务确认归属或临时兜底（与 S4 结论联动）。

**B3. 存量"xxx-视频"站点行处置**
- 并入业务站点后，旧视频站点行：**标离线保留（推荐，不删除，保留历史告警/工单追溯）** / 删除 / 其他；
- 处置清单分三类给出：**可归并 / 无通道对应（僵尸行）/ 名称冲突**（与 7.3-c 联动，后两类须覆盖）；
- 请确认处置方式（含旧行"数据侧可过滤标识"，与 7.3-d 联动）。

**B4. `#5#` 摘除规则**
- 站点视频通道全部消失时是否摘除 `#5#`：建议**不自动摘除**（视频消失不等于站点不再有视频监测，设备离线状态即可表达）；如业务要求摘除，需明确触发规则。

### 3.4 hltgq-device：评审通过后的实施项（供各方知悉）

- 匹配：复用并增强现有匹配链（`resolveParentId`）；
- 站点维护：`epjutj` 追加/维护 `#5#`（幂等，不重复追加）；
- 设备维护：设备 `site` 指向业务站点 ID，同站点多设备（1:N），`status`/位置随通道同步；
- 关系映射调整：通道→站点的关联从"站点表 `devicecode`=通道 code"改为"设备表 `code`=通道 code → 设备表 `site`（业务站点）"。受影响点位清单如下（对应 7.3-b 要求，逐项标注调整方式）：

| # | 点位 | 现状口径 | 调整方式 |
|---|---|---|---|
| 1 | `StationStatusSyncService`（站点同步） | 建"xxx-视频"独立站；写站点 `zebpsu`/`mivbcz`/`ahieto`；通道消失时站点标离线 | 匹配业务站点→追加 `#5#`（失败按 S4 方案 A 兜底）；停写站点 `zebpsu`/`mivbcz`/`ahieto`（S1/S2；7.3-a 答复见 8.2-1）；通道消失只联动设备 `status` 标离线 |
| 2 | `DeviceTableService`（设备维护） | 设备 `site`=视频站点 ID（1:1） | `site`=业务站点 ID（1:N）；启动迁移扩展：设备重指 + 历史告警/工单 `site` 更新 |
| 3 | `GET /api/dahua/channel-info`（`findSiteId`） | `siteId`=视频站点 ID | `siteId`=业务站点 ID（改按设备表 `code`→`site` 解析）；响应结构不变；H5 弹窗宿主关联随之指向业务站点（展示归前端） |
| 4 | `GET /api/dahua/video/patrol-stats`（巡检统计，site 数据统计页「视频数据」行数据源） | 参与通道数=站点表 `epjutj` 含 `#5#` 去重 `devicecode` | 改按"设备表 `type='#5#'` 的 `code` 集合"取数（`countPatrolChannels` 与聚合 SQL 的过滤子查询同步改）；否则分母失真、分子过滤失效 |
| 5 | 巡检留痕写入（`VideoPatrolRecordService.saveRound`） | 按 `channel_code` 落库，无站点字段 | **不受影响** |
| 6 | 事件→站点（`VideoEventService.resolveStation`） | 站点表视频行解析（id/名称/位置） | 改为经"设备表 `code`→`site`"解析业务站点；告警 content 站点名取业务站点名 |
| 7 | 告警→站点（`VideoAlertService.resolveSite` 等） | `site`=视频站点 ID；`resolveSite` 未限定视频类型（隐患） | 改为业务站点解析；`site`=业务站点 ID、`device` 不变；顺带统一各解析点的 `#5#` 类型限定 |
| 8 | 工单联动（`WorkOrderService`） | 匹配键 `site+device+content`；`resolveOrg` 按 `site` 查站点表 `iofhpi` 判库上/库下 | 匹配键不变；部门归属随 `site` 换指可能变化（视频行站码多空→默认库下；业务行有站码）——迁移后核对 |
| 9 | H5 告警查询（`AlertQueryService`）/ 事件回调入口（`DahuaEventCallbackController`） | 按 `device` 关联 / 纯转发 | **不受影响** |

- 存量迁移：按评审结论合并站点、更新设备 `site`、更新告警/工单 `site`；
- 联调按日志化惯例：匹配结果、追加/摘除动作全部打印日志，部署后从服务器日志核对。

## 四、需要达成什么效果（验收标准）

### 4.1 数据形态（验收口径）

| 项 | 现状 | 目标 |
|---|---|---|
| 站点表视频站点行 | 每个通道一行独立"视频站点"（含"xxx-视频"） | 并入业务站点；匹配失败仅兜底行（按 S4 结论） |
| 业务站点 `epjutj` | 不含 `#5#` | 含 `#5#`（如 `#1#\|#4#\|#5#`），追加幂等 |
| 站点-设备关系 | 1:1 | **1:N**，设备 `site` 指向业务站点 ID |
| 设备匹配键 | `code`=通道 devicecode | 不变（`code` 唯一） |
| 视频在线状态落位 | 站点 `zebpsu` | **设备表 `status`**（站点 `zebpsu` 不再由视频驱动，按 S2 结论） |
| 站点命名 | 产生"xxx-视频"影子站点 | 不再产生；站点名保持业务原名 |
| 存量旧站点行 | — | 按 B3 结论处置（推荐标离线保留） |

### 4.2 功能效果

1. **站点视图正确**：一个业务站点同时呈现多监测类型（水位/雨量/视频等），站点下可查看/管理多台视频设备；
2. **接入可扩展**：新增视频通道自动匹配挂靠；匹配失败兜底并在后续轮次自动重试合并；
3. **跨服务一致**：站点表/设备表在 hltgq-device、hltgq-mq、hltgq-site 三方视角下关系一致（站点-设备 1:N、无影子站点、无同 devicecode 混写）。

### 4.3 验收清单

- [ ] 存量迁移后：视频设备全部挂在业务站点下，对应站点 `epjutj` 含 `#5#`；
- [ ] 新通道接入：匹配成功自动挂靠；失败进入待挂靠清单（日志可查），下轮自动重试；
- [ ] 幂等：重复同步不重复追加 `#5#`、不产生重复设备；
- [ ] 视频离线/恢复：设备表 `status` 正确变化，站点 `zebpsu` 不被视频同步改写；
- [ ] 告警/工单：`site`=业务站点 ID、`device`=视频设备 ID，恢复闭环按三字段匹配不断裂；
- [ ] 巡检统计口径：`patrol-stats` 参与通道数改源后与实际通道一致（不再含僵尸站行）；
- [ ] 附属行为核对：存量设备名处置（按 8.2-2 结论）、工单库上/库下归属（`resolveOrg` 随 `site` 换指重新核对）；
- [ ] 回退能力：迁移期保留旧站点行与旧关联，可回退到改造前关系。
