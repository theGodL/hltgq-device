# 站点-设备架构改造 · 数据迁移执行手册

> 依据：《站点-设备数据架构改造评审说明.md》11.5（迁移执行方案）+ 11.5.3（窗口执行序）+ 11.5.4（对账）。
> 执行性质：**写操作**（UPDATE），在迁移窗口内由具备写权限的一方执行（DBA / 运维）；本目录 SQL 已按幂等设计，可分批、可重跑。
> 本库实测坑（务必遵守）：① 字符串拼接一律 `concat()`——本库 `||` 实测返回 `false`；② 否定式判定（`NOT LIKE`/`<> ''`）一律 `COALESCE(列,'')` 包裹，否则 NULL 行被误排除。

## 窗口执行序（11.5.3 定案）

```
停旧同步服务 → 快照原值（重导四张映射 CSV，即回退基线）→ 跑 m1 校验
→ m2 灰度（6 台，五动作）→ m3 灰度对账 → 观察
→ m2 全量（169 台，五动作）→ m3 全量对账
→ 启动新代码 → 部署后观察（m3 观察节）
```

**关键纪律**：

1. **先停旧同步服务**：旧逻辑在窗口内运行会按 devicecode 回写旧行 `zebpsu`（使动作 5 失效）并使映射原值漂移（回退基线失真）；
2. **先快照再迁移**：四张映射 CSV 是回退基线——用 `dry-run/DryRunExport.java` 重导（执行时点数据；工具与复现见 `dry-run/dry-run说明.md`），版本库 + 服务器双份；
3. **每步核对行数**：`m2` 每条 UPDATE 返回的 `UPDATE n` 与手册期望值比对，不符即停、查因后再继续；
4. **失败处理**：任一批对账不过关 → 用 `m4` 回退该批（可按 id 名单限定），修复后重跑；
5. 全部对账通过前，**不要启动新代码**（新代码上线后旧行 `zebpsu` 不会被回写，但窗口纪律仍以 11.5.3 为准）。
