**"56 条名称差异"到底指什么（白话版）**

先说结论：**56 条只是"设备显示名"不好看/写错了，设备本身一条不少、编码全部对得上，不影响视频能不能播、告警能不能出。**

| 类型 | 条数 | 客户看到的问题 | 举例 |

仍要业务确认后改挂，否则告警/巡检会算到错误站点头上。

## 6. 根因（代码机制评审）

| # | 机制 | 位置 | 后果 |
|---|------|------|------|
| R1 | `name` 只在 `createDevice` 写入一次，`syncDeviceState` 仅更新 `status`/`wlcvig` | `DeviceTableService` L234-290、L301-345 | 设备名永久冻结在首次同步值，ICC 改名后库内不跟随 |
| R2 | `lookupOrCreateDevice` 在 code 查不到时**按 name 兜底**匹配 | `DeviceTableService` L167-181 | 新通道与旧行同名时被吞并，不新建、不报错；21 条缺失的**直接根因** |
| R3 | 设备名取 `deviceNameOf(stationName)`（站点名），不是通道名 | `StationStatusSyncService` L239 | 同一 NVR 下所有通道共用站点名 → 必然同名 → 触发 R2 |
| R4 | `resolveBusinessSite` 候选为 nvrName/去上下游/别名/orgName，**不含通道名** | `StationStatusSyncService` L786-821 | 集岭 18 条通道全部解析到「集岭管理所」站，名称全部为"集岭管理所摄像机#" |

| R6 | 过滤组织通道永不同步 | L65 `FILTERED_ORG_NAMES` | 16 条属设计内，不算缺陷 |
| R7 | 告警侧 `resolveSite` 先按设备表 `code → site` 解析，查不到即跳过，**不走到** `resolveOrCreateDevice` 的兜底创建 | `VideoAlertService` L157-167、L364-396 | 未入库通道的巡检故障**完全不产生告警/工单**；21 条缺失通道实测最近 24h 0 条告警 |

**R2+R3+R4 的组合效果**（已用 21 条缺失实测验证）：
新通道 → 解析到站点 → 设备名=站点名+摄像机# → 与既有行同名 → name 兜底命中旧行 → 返回旧 id（不做任何写入）→
`stats.deviceCreated++` 仍错误计数 → 表面"同步成功"，实际数据缺口永久存在。

**R7 的连带效果**：设备缺口不会在告警侧暴露——巡检有结果、留痕有记录，但故障事件被静默丢弃，
形成"看得见巡检记录、看不到告警"的假象。

## 7. 处置方案

### P0 删除 25 条编码残留（**已裁定：全链路删除**）

业务裁定（2026-10-20）：这 25 条确认大华侧不存在、不再接入，其历史告警、工单、设备行**全部物理删除**，
不保留悬空记录，也不要求先关闭未关闭记录。

脚本 `m10-purge-stale-video-devices.sql`（简版，只保留备份与删除）：

1. 第 1 节备份（已执行并通过行数核对）：设备 25 / id 清单 25 / 告警 100 / 工单 100，
   `CREATE TABLE IF NOT EXISTS`，重跑自动跳过；清单表 `t_auto_hltgq_purge_video_ids_20261020` 为删除统一引用源，勿删；
2. 第 2 节删除：先 `work_order`（引用告警/设备）→ 再 `alert` → 最后 `device`
   （设备删除谓词叠加 `id ∈ 清单 ∩ type LIKE '%#5#%' ∩ status='#2#'`，防误删在线/非视频行），
   期望返回 100 / 100 / 25；
3. 删除后核对：清单内设备 0、告警引用 0、工单引用 0，视频设备总数 225→200；
4. 重启服务（`deviceCache` 是 code→deviceId 永久缓存，不重启会继续用已删设备 id 写新告警/工单）。

保留物：巡检历史 22549 条（按 `channel_code` 留痕）、25 条设备所挂站点行、三张备份表。

> **重要口径**：告警表 `device` 与工单表 `device` 存的是**设备表 id**（不是站点 id，也不是 code），
> 删除前已实测引用面：告警 100、工单 100、其余 9 张业务表 0、无外键。

### P1 修复同步逻辑（**已实施，2026-10-20**）

按"设备名完全跟随大华"的裁定落地，改动集中在 4 个类：

1. `DeviceTableService`
   - `deviceNameOf(站点名)` 改为 `channelNameOf(通道名)`：**原样返回 ICC 通道名**，
     不再拼"站点名 + 摄像机#"（设备已挂在站点下，不再需要靠名字区分站点）；
   - `lookupOrCreateDevice`：code 能查到时**只按 code 匹配**，不再按 name 兜底；
     name 兜底仅保留给"历史 code 为空"的行，命中后回填 code（同名但已有其他 code 的行绝不复用，修 R2）；
   - 新增 `updateDeviceName(code, name)`：按 code 精确更新，`name IS DISTINCT FROM ?` 有变化才写库（修 R1）。
2. `StationStatusSyncService`
   - 新通道建设备改用 `channelNameOf(ch.name)`（修 R3）；
   - `syncDeviceState` 每轮增加 `updateDeviceName(ch.devicecode, ch.name)`，ICC 改名后库内自动跟随（修 R1/R4 表现）；
   - 新增 `ensureDeviceRegistered(devicecode)`：通道未入库时按 ICC 设备树即时补建并挂站（供告警/事件侧调用）。
3. `VideoAlertService`
   - `reportFault`：`resolveSite` 为空时先调 `ensureDeviceRegistered`，补建成功后重试解析（修 R7）；
   - `resolveOrCreateDevice`：设备已存在直接按 code 取 id（不触发 ICC 遍历）；需创建时优先用 ICC 通道名。
4. `VideoEventService`
   - `alarmStat=1` 且站点解析为空时同样先补建再重试；设备名优先用 ICC 通道名（同类 R7 问题）。

单测已同步更新，全量 147 个测试通过。

### P2 补建 21 条缺失（**已裁定：代码自动补建**）

不手工 INSERT。P1 发布后有两道自动补建入口：

- **站点同步轮**（每小时/启动即跑）：按 ICC 通道名建设备并挂靠业务站或兜底站；
- **告警/事件侧即时补建**：巡检或智能事件先遇到未入库通道时，`ensureDeviceRegistered` 立即补建再重试，
  不必等下一轮同步。

验证口径：删除后设备立即为 **200**（199 已匹配通道 + 1 条 `code` 空的流量计）；
执行 `m11` 修正流量计类型后为 **199**；服务启动并等首轮同步完成后，21 条缺失通道补建为设备，
设备总数为 **220**（= ICC 视频通道数），巡检通道池 **220 = 199 已匹配 + 21 补建**，
21 条缺失通道开始产生告警/工单、前端可点播。
若 21 条仍有缺，查同步日志的站点解析与设备创建计数，不再手工补数据。

### P3 名称修正（**已裁定：随同步自动归一，无需人工分批**）

56 条名称差异由 `updateDeviceName` 每轮对齐 ICC 通道名，首轮同步后自动归零；
143 条前缀一致的设备名也会一并收敛为纯通道名（去掉"摄像机#"后缀）。
人工只需跟进 **7 条挂站语义错位**（5.6，其中 1000272 / 1000301 最严重）：
改名后显示会正确，但 `site` 仍指向旧站，需业务确认后改挂。

### P4 孤立视频站清理（二次确认）

删除 25 条设备后，站点表中曾作为兜底站的「大门外-视频」「南山寺节制闸-视频」等行可能变成零设备视频站。
本次不处置；待 P1/P2 完成、同步稳定后，按 `epjutj='#5#' AND 无设备指向` 复查再定。
